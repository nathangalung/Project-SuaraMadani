A path marked "(planned)" in a Where column does not exist yet.

How to read this file:
- One table per research domain. Every concept from the research has exactly one row.
- **Verdict**: `adopt-now` (build in Phase 0 or Phase 1), `adopt-later` (build when the trigger fires), `not-needed` (do not build). "(changed)" means the final verdict differs from the research verdict, and the reason is in the row or in [Conflicts Between Rows](#conflicts-between-rows).
- Numbers (timeouts, pool sizes, quotas, limits) are not repeated here. They live once in [architecture.md › Starting Values](architecture.md#starting-values), which names the code file that holds each running value.
- **[unverified]** marks a claim no source confirmed. Each one is assigned to a Phase 0 spike in [architecture.md › Phase 0 Spikes](architecture.md#phase-0-spikes).
- Product behavior follows PLAN.md plus the four approved changes (login at step 7, only merged issues public, rating after "Diklaim selesai" with distribution and n hidden below 10, formal "Anda" copy with a 6+1 step form). The user decided the 20 product proposals and the open product questions on 13 October 2026; those answers are final and are recorded in [architecture.md › Confirmed Product Decisions](architecture.md#confirmed-product-decisions), where "item N" and "Question N" are defined. Rows below already follow them.
- "PLAN" means PLAN.md in this repository. "Phase N" means PLAN §13 "Fase N".
- Where research picked a concept in two domains, the second row is a cross-reference to the row that owns the decision.

## Key Decision Records

Short records for decisions that shape code. Each has context, decision and consequences; the register rows hold triggers and sources.

### ADR-01 Edge Cache Headers

- **Context:** Anonymous reads must come from Cloudflare Free. A plain `s-maxage` header would make Cloudflare ignore `stale-if-error`, so PLAN §10.6 adopts the CDN header pair and keeps `s-maxage=60` only as a fallback. A cached error page or a cached per-visitor value is a correctness and privacy bug.
- **Decision:** One helper, `server/middleware/cache-headers.ts`, decides headers from the route and the status. Public pair (with `stale-while-revalidate` and `stale-if-error` on the CDN header) only on status 200 and the canonicalizing 301. `no-store` on 400 and above. `private, no-store` on every private route listed in architecture.md (Caching Layers and Invalidation: `/lapor/*`, its success page, `/lacak`, `/masuk`, `/isu/*/laporkan`, `/kelola/*`, `/admin/*`, `/api/upload/*`, `/healthz*`) and on any session response. The bypass rule matches `__Secure-sm.session_token` exactly. No GET response contains a per-visitor value. Because `no-transform` stops Cloudflare from compressing, the origin gzips the `no-transform` text and JSON responses itself and adds `Vary: Accept-Encoding` (rule and trade-offs in architecture.md, Caching Layers and Invalidation).
- **Consequences:** An e2e test covers public pages, every `/lapor` step, a forced 503 and the cookie name after login. If the Phase 0 spike shows `bypass_by_default` ignores `Cloudflare-CDN-Cache-Control`, the fallback is the `s-maxage=60` header (PLAN §10.6) without `stale-if-error`.

### ADR-02 Cache Invalidation and Redaction

- **Context:** Takedowns carry a legal clock (1×24 h, 4 h urgent). A URL list misses query variants, `.data` URLs, OG images, public evidence and the R2 media domain. A web request can die after COMMIT, and personal data can survive in history tables.
- **Decision:** Routine changes purge their URLs from `web` after COMMIT, once, without a queue. `shared/status.ts` defines `reducesVisibility`; those transitions redact the issue title and summary in place (originals to admin-only `redaction_originals`; `audit_log` holds only column names and keyed HMAC hashes, for example `issue.redact`), and send a `takedown` job in the same transaction. `issue_versions` is not built yet, and redaction does not reach timeline notes or agency responses. Audit actions are the closed list `AUDIT_ACTIONS` in `shared/moderation.ts` (`report.*`, `issue.*`, `account.close_minor`, `account.close`, `evidence.decide`, `evidence.download_original`, `complaint.submit|decide|appeal|appeal_decide`, `member.*`, `settings.*`, `campus.create`, `demand.*`; listed in architecture.md Schema notes). Routine purges also clear `/data` and every OG image version, because the OG PNG draws the title and place. The job deletes public files and R2 objects and purges by hostname (tenant host and media host), retrying with backoff at concurrency 1 and recording `purge_status`; `/healthz/jobs` pages when it is not `done` after 10 minutes.
- **Consequences:** Every reader, including the apex national view and the Phase 2 exports, sees only redacted data. A takedown refills one tenant's cache, not every tenant's. A test redacts a seeded string and finds it nowhere outside `redaction_originals`.

### ADR-03 Tenancy, Roles and RLS

- **Context:** One database holds every campus. RLS fails silently on SELECT. A BYPASSRLS role is the one object that can defeat tenant isolation, and the user put the apex national view in Phase 1 (item 6), so one cross-tenant read path exists from launch.
- **Decision:** `ENABLE` and `FORCE` RLS on every tenant table, tenant set per transaction through `withTenant`. Roles `sm_migrator`, `sm_app`, `sm_media`, `sm_backup` and the NOLOGIN `sm_aggregates` created by `infra/initdb.sql`; `pg-hba.conf` allows only `scram-sha-256`, per role from its own subnet or the local socket. Health and maintenance checks read tenant tables per org inside `withTenant`. A catalog test fails CI for any reachable table or view without RLS that is not allowlisted. `report_contacts` is insertable by the reporter's transaction but readable only under `app.member_role = 'admin'` (one tenant staff role since migration 0017). `requireRole` uses only the `Host`-derived tenant. The dashboard reads per-org snapshots under RLS. The apex reads one materialized view, `national_aggregates`, owned by `sm_aggregates`, holding only small-n-suppressed counts; `sm_app` has SELECT and `MAINTAIN` on it and nothing else from that role. Forwarding writes into another tenant only through `forwardReport`, one transaction per tenant, with the admin role checked in the source tenant. The WhatsApp tables are global and outside RLS; the sealed credentials are their boundary.
- **Consequences:** Backfills run as `sm_app` per org. Timeouts live in pool config. The one BYPASSRLS role cannot log in, and its only product is a view whose suppression has a test; that the refresh sees every campus on PG 18 with `FORCE` is checked in Phase 0.

### ADR-04 Background Jobs and Outbox

- **Context:** About 3 to 275 reports a day. Every external side effect must not fire for a rolled-back change and must survive retries.
- **Decision:** pg-boss in the same Postgres. Jobs are sent inside the domain transaction with `fromDrizzle`. Fixed queues created by the `migrate` step. DLQs on every side-effect queue until spike P3, alerting through `/healthz/jobs`, which computes queue age in SQL; triage with `db/jobs-cli.ts`. Handlers are idempotent and throw on empty tenant reads (except rows deleted on purpose, which return `skipped`). `worker`, `worker-media` and `worker-whatsapp` run different queue sets from one image; `worker-media` under its own role. Follower fan-out is one job per event, batched in the worker.
- **Consequences:** Report submission does not depend on the workers. CI boots pg-boss on a fresh schema; a pg-boss upgrade is checked on the drill VM, and `deploy.sh` stops the workers before migrating it.

### ADR-05 Evidence Upload Pipeline

- **Context:** PLAN §7 accepts up to 5 files (image or PDF 10 MB, video 50 MB). The user moved the transfer to after the step-7 sign-in (item 2), removed server drafts (item 5) and kept PDF and video (item 1). Cloudflare Free caps one request at 100 MB (**[unverified]** for proxied traffic, P1), so 5 videos cannot share one request. Untrusted files reach image, HEIC, PDF and video decoders.
- **Decision:** Steps 1–6 keep the chosen files in the browser. The step-7 submit creates the report and one `evidence` row per file in `awaiting_upload`; then the browser sends each file in its own authenticated `POST /api/upload/<evidence id>`, accepted only from the report's owner inside a 24 h window, type detected from the first bytes and required to match the manifest row's kind and `EVIDENCE_LIMITS[kind]` (Bun `maxRequestBodySize` is the video limit plus 1 MB), raw body streamed to a temp file in `files/evidence/<org>/` and renamed after hashing, row moved to `received` by compare-and-set and an `evidence` or `evidence-video` job sent. Rows still waiting when the window closes become `missing` (`maintenance-daily`). A per-tenant byte cap per 24 h and upload slots per client IP bound abuse. `worker-media` processes as `sm_media`: sharp for photos, `heif-dec` for HEIC (item 18), ClamAV then `pdftoppm` page images for PDF (item 14), `ffprobe` limits and a 720p transcode for video (items 9, 10), and writes private previews to `files/derived/<org>/`. Admins save one decision per file (`decideEvidence`): boxes on photos and PDF pages (black or mosaic), "no censoring needed", or "Jangan terbitkan" for any kind; a video is published only when it needs none (item 19). When the issue is public, the decision sends `evidence-publish`, which writes public images or copies the video to R2 and re-checks that the issue is still published before it marks the row. Caddy serves only `files/public/<host>` image types with `nosniff` and a sandbox CSP.
- **Consequences:** No anonymous write endpoint, quarantine, upload cookie, GC or unattached file exists (item 13 is moot). A tab discarded between step 5 and the uploads loses the files but not the answers; step 7 or `/lacak` asks for them again (spike P20). The admin queue shows reports whose files are still arriving. A policy brief is the staff exception: a scanned original PDF, served as an attachment (ADR-17).

### ADR-06 Email

- **Context:** The OTP at step 7 gates every first report. Brevo Free allows 300 emails a day. The user chose one email per status change to the reporter and to every follower (item 3).
- **Decision:** One provider at a time through its HTTPS API (`EMAIL_PROVIDER`); Brevo at launch; SES production access requested in Phase 0 and required before the closed pilot (PLAN §12), because the SES sandbox sends only to verified recipients; the SES sender in `server/email.ts` is not built yet. Email codes sent from `web`, not awaited, after `reserveOtp` takes the per-address and provider-day reservation (429 or 503 otherwise); in-flight sends are awaited on shutdown. Since 16 October 2026 a person may choose WhatsApp instead (ADR-16), which does not use the email quota. Every transition of the report state machine emails the reporter, and a unit test checks each one has a follow-up (the receipt on submit is **[proposed]**, architecture.md Open Question 3); reporters follow their issue from the merge; `issue-notify` fans out every issue status change and response to all followers. A daily notification ceiling keeps a reserve of the provider quota for OTP; `email-send` counts under an advisory lock and defers anything above the ceiling to the next morning (item 4). Every send is counted in `email_log`.
- **Consequences:** On a busy day notifications and invitations arrive late (they share the 200 ceiling), but sign-in keeps working. The backlog has no bound until SES carries the volume, so deferrals on two days in a week make SES the default. Brevo down blocks email codes until SES exists and is switched on; accounts with a number can use WhatsApp meanwhile.

### ADR-07 Dashboard and National Aggregates

- **Context:** PLAN §10.6 writes per-org `dashboard_snapshots` and refreshes one national materialized view every 15 minutes, and §5.11 gives national aggregates a separate role. At most 100k reports a year. The user moved the apex national view to Phase 1 (item 6).
- **Decision:** The `aggregate-refresh` job writes one `dashboard_snapshots(org_id, computed_at, payload)` row per org every 15 minutes through `withTenant` as `sm_app`, with small-n suppression in the payload (threshold in architecture.md Starting Values), then runs `REFRESH MATERIALIZED VIEW national_aggregates`. That view is owned by `sm_aggregates` (NOLOGIN, BYPASSRLS), so the refresh, which runs as the owner under `search_path` `pg_catalog, pg_temp`, sees every campus; its query suppresses small cells, names tables with their schema and selects `now() AS computed_at`. `/data` reads the snapshot row and the apex reads the view; both show "Terakhir diperbarui" from `computed_at`, and `/healthz/jobs` pages when either is older than 1 h.
- **Consequences:** One BYPASSRLS role, one materialized view, one `MAINTAIN` grant and one ownership transfer exist in Phase 1, each covered by the catalog and suppression tests and checked in Phase 0. Per-org numbers still need no cross-tenant role. Applied to PLAN §5.11 and §13 (Fase 1) on 13 October 2026.

### ADR-08 Abuse Controls

- **Context:** Campus NAT and mobile CGNAT put many users behind one IP; in-memory counters reset on deploy and split across processes.
- **Decision:** One Cloudflare rule, Turnstile on the four actions (code request, report submit, rating, content complaint; the rating action is built for the tuntutan importance rating at `/tuntutan/:code/nilai`, the issue rating stays Phase 2), per-address and per-number code caps (60 s, 8 a day) and the WhatsApp sender caps (60 an hour, 300 a day), the Better Auth limiter with `CGNAT_LIMIT` (20 per 60 s) on the four code endpoints, SQL quotas under a per-user transaction lock, uploads only from signed-in report owners with a per-tenant byte cap, load shedding, search slots and the 3-character minimum for GETs, and the intake pause (item 11). Identifier-first sign-in and Daftar's uniqueness check reveal whether an account exists; only these limits protect them (accepted exposure, an open question).
- **Consequences:** No in-process limiter for writes besides Better Auth's. Step 7 uses two Turnstile tokens (code request and final submit).

### ADR-09 Idempotency and Concurrency

- **Context:** Double taps on 4G, retried uploads, repeated forwards, several admins per campus, gapless public numbers.
- **Decision:** Browser-minted `submission_id` with a user-scoped unique key and a `RETURNING` branch, never in a URL; evidence rows created by the submit and moved to `received` by compare-and-set on upload; forwarding keyed by `forwarded_from_report_id`; Turnstile duplicates re-run the lookup; CAS on status; `version` on free-text edits; merge locks in a fixed order and rolls back on any changed report; `org_counters` for numbers; whole-transaction retry for report codes.
- **Consequences:** Concurrency tests for submit, repeated upload, repeated forward and merge are part of CI.

### ADR-10 CSRF, Cookies and Multi-Host Auth

- **Context:** Tenant subdomains are same-site. Inside the box the request URL is `http://`. Passkeys need one relying party.
- **Decision:** An Origin check in the root middleware (same origin, or `Sec-Fetch-Site: same-origin`) as the single CSRF control with `SameSite=Lax`; explicit `trustedOrigins` built at boot; host-only cookies; Caddy overwrites `X-Forwarded-Host`; passkey `rpID` at the apex (one passkey for every host; passkeys are not built yet, P5); staff TOTP check in middleware. The apex itself serves only the national view, with no sign-in or form.
- **Consequences:** PLAN does not define cross-campus sign-in, so users sign in separately on each host as a security control. Adding a tenant ends with a `web` restart.

### ADR-11 Code Organization and Dependency Rule

- **Context:** A new team every year; one web client.
- **Decision:** Feature folders; routes call `*.server.ts` functions; `shared/` is pure; `worker/` imports `db/`, `shared/` and the `server/` clients, never `app/`; Biome enforces `components` not importing `features`, the worker rule and no cycles; `.server` naming stops server code reaching the client bundle.
- **Consequences:** No repositories, no DI, no internal HTTP API, and two port types (`EmailSender`, `WhatsAppProvider`).

### ADR-12 Request Pipeline

- **Context:** CSP hashes need the final HTML; React Router dev does not run the custom server.
- **Decision:** cloudflared → Caddy → Hono (`server/app.ts`) → React Router handler with `RouterContextProvider`. Tenant and session resolve in React Router root middleware so dev and production match. Hono owns transport concerns and `/api/*`. Buffered render and CSP in `entry.server.tsx`.
- **Consequences:** The dev path for `/api/*` is a Phase 0 spike.

### ADR-13 Deploy and Migrations

- **Context:** drizzle-orm runs all pending migrations in one transaction and skips older timestamps. SHA rollback does not revert schema.
- **Decision:** Separate build and deploy jobs; a forced SSH command that accepts only a SHA; `migrate` one-off as `sm_migrator` (workers stopped first when pg-boss changes), `up --wait`, SHA check, smoke test per host, `.deployed-history` with UTC times, automatic redeploy of the previous SHA on failure; expand/contract with squawk and a `contract-migration` label; journal-order check. PITR targets a time, so the deploy needs no superuser.
- **Consequences:** Rollback by SHA stays safe for one release, and `deploy.sh` refuses targets older than the last contract migration.

### ADR-14 Storage, Encryption and Backups

- **Context:** One disk holds Postgres, WAL, evidence and Docker's own data, which includes container environment values. A failing archiver fills `pg_wal` and Postgres PANICs. An unmounted LUKS volume makes Docker write plaintext to the root disk. The app tunnel runs in Docker, so it cannot carry the SSH session that unlocks the disk. Every backup sits in one Cloudflare account.
- **Decision:** One LUKS container, three LVs (`pgdata`, `files`, `docker`); the server's age key on the volume; passphrase unlock over a host-level, SSH-only tunnel; mount guards with binds into LV subdirectories; swap off or encrypted per boot; archiver and `backup_runs` checks in `/healthz/jobs`; pgBackRest and restic to separate R2 buckets with bucket locks if Free allows, plus a weekly mirror of the database repository to B2 whose age the server checks with a list-only key; rotation per key type; quarterly restore drill with reconciliation and a tenant-level restore.
- **Consequences:** Every reboot needs a person with Access SSH, but not physical access. TPM2 auto-unlock stays out, so a stolen server stays locked.

### ADR-15 Cross-Campus Forwarding

- **Context:** A report can concern another campus's region or scope. The user chose no automatic routing: a report stays at the receiving campus, whose admins can forward it, which copies it and logs it in `audit_log` (Question 5). `withTenant` sets one tenant per transaction.
- **Decision:** `forwardReport` first locks the report under campus A and moves it to `forwarded` with compare-and-set and A's audit row; then, under B, it inserts the copy with `forwarded_from_report_id`, a new B code, status `in_review`, the reporter's membership in B if missing and an audit row, hard-links the evidence originals into B's directory, sends B's `evidence` jobs and emails the reporter B's tracking link with the original code (original first, so a concurrent reject at A cannot leave a copy at B for a rejected report). `UNIQUE (org_id, forwarded_from_report_id)` makes a retry finish the job without a second copy. `report_contacts` is not copied, because the reporter consented to campus A.
- **Consequences:** Two short transactions instead of one; a failure between them leaves A's original forwarded without a copy at B, which repeating the action resolves (the report page shows whether the copy exists). B's admins see no contact data; the reporter hears from B only through system status emails.

### ADR-16 Sign-Up, Sign-In and WhatsApp Delivery

- **Context:** The user decided on 16 October 2026 that every account holds a full name, an email address and a WhatsApp number, that a returning person signs in with either identifier, and that the person chooses where the code goes: email or WhatsApp. For WhatsApp the user chose an unofficial library after being told that the official Meta WhatsApp Business Platform charges per authentication message (the figure given was about Rp357 plus PPN in Indonesia; not re-checked against Meta's IDR rate card) and needs a verified Meta Business account, and that unofficial WhatsApp Web libraries break WhatsApp's terms, so the sending number can be banned at any time. Better Auth's `phoneNumber` plugin stores codes in plain text, signs in with a password, signs up with a temporary email, and lets admins skip TOTP.
- **Decision:** One Better Auth plugin of our own, `accountOtp`, for both channels (hashed codes, server-side identifier resolution, the two-factor after-hook reattached, the 18+ and phone checks in the user-creation hook). Email codes go out from `web`; WhatsApp codes go through the sealed `whatsapp-send` job to `worker-whatsapp`, which runs Baileys 6.7.24 (npm `baileys`, WhiskeySockets, the newest stable release; 7.0.0 is a release candidate) behind a provider interface. A Meta Cloud API adapter (copy-code authentication template) and a dev adapter (Mailpit) implement the same interface, chosen by `WHATSAPP_PROVIDER`. The superadmin links one dedicated number at `/admin/whatsapp` by QR or pairing code; the session credentials are sealed with a key only `worker-whatsapp` holds. Safety: per-number and sender rate limits, one short plain-text message with no link, a disabled WhatsApp option with a clear message when the sender is down, a visible failure with "Kirim lewat email" when a send fails, and `/healthz/jobs` reporting the sender state.
- **Consequences:** A ban or an outage of the number stops WhatsApp codes but never sign-in, because email always works. The switch path is a config change and a restart of `worker-whatsapp` (`WHATSAPP_PROVIDER=meta` with `META_WA_TOKEN`, `META_WA_PHONE_NUMBER_ID`, `META_WA_TEMPLATE`), after Meta approves the template, at a per-message cost. Triggers to switch: the number is banned, sends fail repeatedly, or the legal entity does not accept the risk. Known gaps (open questions): Daftar verifies only the chosen channel, accounts made before migration 0018 have no number, and identifier-first sign-in reveals whether an account exists. Never link a real number in dev and pick WhatsApp for a seed account. The sender handset is a credential (review round 2): whoever holds it, or a WhatsApp Web session linked to it, could read a live code and sign in as a non-admin user. Codes are sent disappearing (24 h) and the chat is deleted on the sender's devices right after the send; the handset stays locked with the superadmin, no other device is linked to the number, and `/admin/whatsapp` is checked at every on-call handover. A code sent to a number the account has not proven counts as a Daftar code, so Masuk cannot be used to message strangers past the Daftar caps. Second review round 2 (17 October 2026): codes to unproven email addresses have their own share (20 an hour, 60 a day, 10 a day per client address), as WhatsApp already had, so a Daftar flood cannot spend the provider day that proven sign-ins need; a graceful stop of `worker-whatsapp` writes `stopped`, which `/healthz/jobs` treats as deliberate, so the incident lever no longer hides every other alert; `whatsapp_auth` row keys carry an HMAC of the recipient id and contact sessions idle 30 days are pruned; sign-in code identifiers in `verifications` are HMACs and expired rows are deleted daily.

### ADR-17 Tuntutan

- **Context:** The user moved tuntutan to Phase 1 on 16 October 2026: written by admins, never derived from reports, national or regional, broken into subtuntutan because the whole is too complex to resolve at once, each subtuntutan judged on two axes with a dated, sourced history and an optional policy brief, shown on the dashboard map by colour only.
- **Decision:** Six tenant tables with FORCE RLS (migration 0019) and pure state machines in `shared/status.ts`; progress derived in the same transaction as every item change, never typed; CAS on `version`; every change audited and purged, and publish, close, reopen, status changes, notes and published briefs written to the public timeline and emailed to followers (`demand-notify`). Policy briefs are scanned by clamd in `worker-media` (the web stays off the `scan` network), published only by an explicit admin step, and served as a PDF with `nosniff` and a sandbox CSP: the user's exception to the rasterize-only rule for reporter PDFs, because a brief is staff-authored. The served file is a qpdf rewrite without the Info dictionary and catalog XMP (review round 2: an exported brief names its author there, and authorship is public only as "Admin {organisation}"); one brief per subtuntutan is public, a new one replaces the old in the same transaction, and "Tarik dari publik" withdraws one with a timeline row. A complaint about a tuntutan can only keep or hide it (the admins fix their own text). `/data` and home read tuntutan live, not from the 15-minute snapshot, because a hide must take effect at once; the apex counts them exactly in `national_aggregates` (migration 0020). The tuntutan map layer has its own fixed classes (0, 1, 2, 3–4, 5+) and a violet ramp, because a shared report scale would paint every tuntutan province as the hidden-range class "1–4".
- **Consequences:** Two map layers, two hues, so "dark" never means the same number on both. Adding, editing or moving a subtuntutan on a published tuntutan writes no timeline row or email (open question). Brief PDF URLs are purged on hide, withdraw and replace (review round 2). A hidden tuntutan comes back in the state it had before the hide. A closed tuntutan, also while hidden, takes no new subtuntutan, update, brief upload or brief publish until it is reopened; withdrawing a published brief stays possible (second review round 2).

### ADR-18 Tuntutan Category, Citizen Importance and Neutral Copy

- **Decision:** Migration 0024 adds `demands.category` (CHECK from `DEMAND_CATEGORIES`, nullable only for older rows, required by the form and by publish) and `demand_ratings` (FORCE RLS, one row per account per tuntutan, `show_name` default false). The rating rules live in `rating.server.ts`: sign-in, Turnstile, published tuntutan only, withdraw always allowed, the 7-day account age checked at read time, the mean from 10 counted raters. The rating page is a private route like the complaint page, so the cached detail page never loads Turnstile. Home shows "Terbaru" and "Paling Penting Menurut Warga" under the hero; the digest's category and importance text is rendered on the server (`toDigest`) to keep `/` (129.89 KB) and `/data` (149.69 KB) under their budgets. Neutral copy is advice in the editor (`neutralFindings`), never a gate, because a word list cannot judge context.
- **Consequences:** "Paling Penting Menurut Warga" is an exception, for tuntutan only, to PLAN §5.8 and to `docs/mockup-port-map.md`, which dropped the mockup's "Paling didukung" ranking; issues still have no support ranking. The importance mean is the one place a single average is shown, unlike the issue rating (PLAN §5.7), because it orders the home list. Ratings are not audited, not emailed and not purged; anonymous visitors see a change after the 60 s CDN TTL. Closing a reporter's account at a campus deletes their ratings there. `/privasi` does not yet describe named raters (PLAN §14 item 30). `/` has 0.11 KB left of its 130 KB budget, so the next home change needs a saving first.
