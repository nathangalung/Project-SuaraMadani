How to read this file:
- One table per research domain. Every concept from the research has exactly one row.
- **Verdict**: `adopt-now` (build in Phase 0 or Phase 1), `adopt-later` (build when the trigger fires), `not-needed` (do not build). "(changed)" means the final verdict differs from the research verdict, and the reason is in the row or in [Conflicts Between Rows](#conflicts-between-rows).
- Numbers (timeouts, pool sizes, quotas, limits) are not repeated here. They live once in [architecture.md › Starting Values](architecture.md#starting-values), which names the code file that holds each running value.
- **[unverified]** marks a claim no source confirmed. Each one is assigned to a Phase 0 spike in [architecture.md › Phase 0 Spikes](architecture.md#phase-0-spikes).
- Product behavior follows PLAN.md plus the four approved changes (login at step 7, only merged issues public, rating after "Diklaim selesai" with distribution and n hidden below 10, formal "Anda" copy with a 6+1 step form). The user decided the 20 product proposals and the open product questions on 13 October 2026; those answers are final and are recorded in [architecture.md › Confirmed Product Decisions](architecture.md#confirmed-product-decisions), where "item N" and "Question N" are defined. Rows below already follow them.
- "PLAN" means PLAN.md in this repository. "Phase N" means PLAN §13 "Fase N".
- Where research picked a concept in two domains, the second row is a cross-reference to the row that owns the decision.

## Key Decision Records

Short records for decisions that shape code. Each has context, decision and consequences; the register rows hold triggers and sources.

### ADR-01 Edge Cache Headers

- **Context:** Anonymous reads must come from Cloudflare Free. A plain `s-maxage` header would make Cloudflare ignore `stale-if-error`, so PLAN §10.6 adopts the CDN header pair and keeps `s-maxage=60` only as a fallback. A cached error page or a cached per-visitor value is a correctness and privacy bug.
- **Decision:** One helper, `server/middleware/cache-headers.ts`, decides headers from the route and the status. Public pair (with `stale-while-revalidate` and `stale-if-error` on the CDN header) only on status 200 and the canonicalizing 301. `no-store` on 400 and above. `private, no-store` on every private route listed in architecture.md (Caching Layers and Invalidation: `/lapor/*`, its success page, `/lacak`, `/masuk`, `/isu/*/laporkan`, `/kelola/*`, `/admin/*`, `/api/upload/*`, `/healthz*`) and on any session response. The bypass rule matches `__Host-sb.session_token` exactly. No GET response contains a per-visitor value. Because `no-transform` stops Cloudflare from compressing, the origin gzips the `no-transform` text and JSON responses itself and adds `Vary: Accept-Encoding` (rule and trade-offs in architecture.md, Caching Layers and Invalidation).
- **Consequences:** An e2e test covers public pages, every `/lapor` step, a forced 503 and the cookie name after login. If the Phase 0 spike shows `bypass_by_default` ignores `Cloudflare-CDN-Cache-Control`, the fallback is the `s-maxage=60` header (PLAN §10.6) without `stale-if-error`.

### ADR-02 Cache Invalidation and Redaction

- **Context:** Takedowns carry a legal clock (1×24 h, 4 h urgent). A URL list misses query variants, `.data` URLs, OG images, public evidence and the R2 media domain. A web request can die after COMMIT, and personal data can survive in history tables.
- **Decision:** Routine changes purge their URLs from `web` after COMMIT, once, without a queue. `shared/status.ts` defines `reducesVisibility`; those transitions redact the issue title and summary in place (originals to admin-only `redaction_originals`; `audit_log` holds only column names and keyed HMAC hashes, for example `issue.redact`), and send a `takedown` job in the same transaction. `issue_versions` is not built yet, and redaction does not reach timeline notes or agency responses. Audit actions are the closed list `AUDIT_ACTIONS` in `shared/moderation.ts` (`report.*`, `issue.*`, `account.close_minor`, `account.close`, `evidence.decide`, `evidence.download_original`, `complaint.submit|decide|appeal|appeal_decide`, `member.*`, `settings.*`, `campus.create`, `demand.*`; listed in architecture.md Schema notes). Routine purges also clear `/data` and every OG image version, because the OG PNG draws the title and place. The job deletes public files and R2 objects and purges by hostname (tenant host and media host), retrying with backoff at concurrency 1 and recording `purge_status`; `/healthz/jobs` pages when it is not `done` after 10 minutes.
- **Consequences:** Every reader, including the apex national view and the Phase 2 exports, sees only redacted data. A takedown refills one tenant's cache, not every tenant's. A test redacts a seeded string and finds it nowhere outside `redaction_originals`.

### ADR-03 Tenancy, Roles and RLS

- **Context:** One database holds every campus. RLS fails silently on SELECT. A BYPASSRLS role is the one object that can defeat tenant isolation, and the user put the apex national view in Phase 1 (item 6), so one cross-tenant read path exists from launch.
- **Decision:** `ENABLE` and `FORCE` RLS on every tenant table, tenant set per transaction through `withTenant`. Roles `sb_migrator`, `sb_app`, `sb_media`, `sb_backup` and the NOLOGIN `sb_aggregates` created by `infra/initdb.sql`; `pg-hba.conf` allows only `scram-sha-256`, per role from its own subnet or the local socket. Health and maintenance checks read tenant tables per org inside `withTenant`. A catalog test fails CI for any reachable table or view without RLS that is not allowlisted. `report_contacts` is insertable by the reporter's transaction but readable only under `app.member_role = 'admin'` (one tenant staff role since migration 0017). `requireRole` uses only the `Host`-derived tenant. The dashboard reads per-org snapshots under RLS. The apex reads one materialized view, `national_aggregates`, owned by `sb_aggregates`, holding only small-n-suppressed counts; `sb_app` has SELECT and `MAINTAIN` on it and nothing else from that role. No code writes into another tenant: forwarding (`forwardReport`, the only cross-tenant write) was removed on 25 October 2026 (ADR-26). The WhatsApp tables are global and outside RLS; the sealed credentials are their boundary.
- **Consequences:** Backfills run as `sb_app` per org. Timeouts live in pool config. The one BYPASSRLS role cannot log in, and its only product is a view whose suppression has a test; that the refresh sees every campus on PG 18 with `FORCE` is checked in Phase 0.

### ADR-04 Background Jobs and Outbox

- **Context:** About 3 to 275 reports a day. Every external side effect must not fire for a rolled-back change and must survive retries.
- **Decision:** pg-boss in the same Postgres. Jobs are sent inside the domain transaction with `fromDrizzle`. Fixed queues created by the `migrate` step. DLQs on every side-effect queue until spike P3, alerting through `/healthz/jobs`, which computes queue age in SQL; triage with `db/jobs-cli.ts`. Handlers are idempotent and throw on empty tenant reads (except rows deleted on purpose, which return `skipped`). `worker`, `worker-media` and `worker-whatsapp` run different queue sets from one image; `worker-media` under its own role. Follower fan-out is one job per event, batched in the worker.
- **Consequences:** Report submission does not depend on the workers. CI boots pg-boss on a fresh schema; a pg-boss upgrade is checked on the drill VM, and `deploy.sh` stops the workers before migrating it.

### ADR-05 Evidence Upload Pipeline

- **Context:** PLAN §7 accepts up to 5 files (image or PDF 10 MB, video 50 MB). The user moved the transfer to after the step-7 sign-in (item 2), removed server drafts (item 5) and kept PDF and video (item 1). Cloudflare Free caps one request at 100 MB (**[unverified]** for proxied traffic, P1), so 5 videos cannot share one request. Untrusted files reach image, HEIC, PDF and video decoders.
- **Decision:** Steps 1–6 keep the chosen files in the browser. The step-7 submit creates the report and one `evidence` row per file in `awaiting_upload`; then the browser sends each file in its own authenticated `POST /api/upload/<evidence id>`, accepted only from the report's owner inside a 24 h window, type detected from the first bytes and required to match the manifest row's kind and `EVIDENCE_LIMITS[kind]` (Bun `maxRequestBodySize` is the video limit plus 1 MB), raw body streamed to a temp file in `files/evidence/<org>/` and renamed after hashing, row moved to `received` by compare-and-set and an `evidence` or `evidence-video` job sent. Rows still waiting when the window closes become `missing` (`maintenance-daily`). A per-tenant byte cap per 24 h and upload slots per client IP bound abuse. `worker-media` processes as `sb_media`: sharp for photos, `heif-dec` for HEIC (item 18), ClamAV on every original before any decoder (ASVS V5.4.3), `pdftoppm` page images for PDF (item 14), `ffprobe` limits and a 720p transcode for video (items 9, 10), and writes private previews to `files/derived/<org>/`. Admins save one decision per file (`decideEvidence`): boxes on photos and PDF pages (black or mosaic), "no censoring needed", or "Jangan terbitkan" for any kind; a video is published only when it needs none (item 19). When the issue is public, the decision sends `evidence-publish`, which writes public images or copies the video to R2 and re-checks that the issue is still published before it marks the row. Caddy serves only `files/public/<host>` image types with `nosniff` and a sandbox CSP.
- **Consequences:** No anonymous write endpoint, quarantine, upload cookie, GC or unattached file exists (item 13 is moot). A tab discarded between step 5 and the uploads loses the files but not the answers; step 7 or `/lacak` asks for them again (spike P20). The admin queue shows reports whose files are still arriving. A policy brief is the staff exception: a scanned original PDF, served as an attachment (ADR-17). Since 21 October 2026 the same URL also takes resumable tus `HEAD` and `PATCH` requests under the same rules, so a dropped connection resumes from the last stored byte instead of byte 0 (ADR-21).

### ADR-06 Email

- **Context:** The OTP at step 7 gates every first report. Brevo Free allows 300 emails a day. The user chose one email per status change to the reporter and to every follower (item 3). Since 25 October 2026 followers get no email (ADR-26).
- **Decision:** One provider at a time through its HTTPS API (`EMAIL_PROVIDER`); Brevo at launch; SES production access requested in Phase 0 and required before the closed pilot (PLAN §12), because the SES sandbox sends only to verified recipients. The SES sender (`sesSender` in `server/email.ts`, 21 October 2026) calls SES API v2 `SendEmail` over HTTPS with SigV4 from aws4fetch's `AwsV4Signer` and classifies errors by the AWS error type (architecture.md Email, SES). Library choice (tooling-eval): aws4fetch 1.0.20 (MIT, no dependencies, about 65 KB unpacked, WebCrypto, about 6 million weekly downloads, released 28 August 2024, so it clears the 14-day rule) over `@aws-sdk/client-sesv2` 3.1154.0 (about 2 MB unpacked plus 11 direct dependencies and the Smithy runtime, with releases most weeks, which means Renovate churn for one call) and over hand-written SigV4 (signing code we would own and have to test against AWS's suite ourselves). Only the signer is used: `AwsClient.fetch` would use the global `fetch` and retry up to 10 times on top of pg-boss. aws4fetch signs `host` and `x-amz-date`, not `content-type`, by design; the body hash is signed. Known risk: no release since August 2024, accepted because SigV4 is a frozen protocol. Email codes sent from `web`, not awaited, after `reserveOtp` takes the per-address and provider-day reservation (429 or 503 otherwise); in-flight sends are awaited on shutdown. Since 16 October 2026 a person may choose WhatsApp instead (ADR-16), which does not use the email quota. Every transition of the report state machine emails the reporter, and a unit test checks each one has a follow-up (the receipt on submit is **[proposed]**, architecture.md Open Question 3); reporters follow their issue from the merge; `issue-notify` fanned out every issue status change and response to all followers until 25 October 2026; since then nothing queues it and its handler only drains old jobs (ADR-26). A daily notification ceiling keeps a reserve of the provider quota for OTP; `email-send` counts under an advisory lock and defers anything above the ceiling to the next morning (item 4). Every send is counted in `email_log`.
- **Consequences:** On a busy day notifications and invitations arrive late (they share the 200 ceiling), but sign-in keeps working. The backlog has no bound until SES carries the volume, so deferrals on two days in a week make SES the default; that needs SES production access and a code change to `EMAIL_QUOTA` (`shared/notifications.ts`, still Brevo's 300, 200 and 100), because switching `EMAIL_PROVIDER` alone gives redundancy, not volume (user decision: quota as an env value). Brevo down blocks email codes until `EMAIL_PROVIDER=ses` is set and the services restart; accounts with a number can use WhatsApp meanwhile. SES has no idempotency key, so a send whose response is lost can be delivered twice on retry, as with Brevo whose key coverage is unverified (P17).

### ADR-07 Dashboard and National Aggregates

- **Context:** PLAN §10.6 writes per-org `dashboard_snapshots` and refreshes one national materialized view every 15 minutes, and §5.11 gives national aggregates a separate role. At most 100k reports a year. The user moved the apex national view to Phase 1 (item 6).
- **Decision:** The `aggregate-refresh` job writes one `dashboard_snapshots(org_id, computed_at, payload)` row per org every 15 minutes through `withTenant` as `sb_app`, with small-n suppression in the payload (threshold in architecture.md Starting Values), then runs `REFRESH MATERIALIZED VIEW national_aggregates`. That view is owned by `sb_aggregates` (NOLOGIN, BYPASSRLS), so the refresh, which runs as the owner under `search_path` `pg_catalog, pg_temp`, sees every campus; its query suppresses small cells, names tables with their schema and selects `now() AS computed_at`. `/data` reads the snapshot row and the apex reads the view; both show "Terakhir diperbarui" from `computed_at`, and `/healthz/jobs` pages when either is older than 1 h.
- **Consequences:** One BYPASSRLS role, one materialized view, one `MAINTAIN` grant and one ownership transfer exist in Phase 1, each covered by the catalog and suppression tests and checked in Phase 0. Per-org numbers still need no cross-tenant role. Applied to PLAN §5.11 and §13 (Fase 1) on 13 October 2026.

### ADR-08 Abuse Controls

### ADR-09 Idempotency and Concurrency

- **Context:** Double taps on 4G, retried uploads, repeated forwards (until forwarding was removed on 25 October 2026, ADR-26), several admins per campus, gapless public numbers.

### ADR-10 CSRF, Cookies and Multi-Host Auth

- **Context:** Tenant subdomains are same-site. Inside the box the request URL is `http://`. Passkeys need one relying party.
- **Decision:** An Origin check in the root middleware (same origin, or `Sec-Fetch-Site: same-origin`) as the single CSRF control with `SameSite=Lax`; explicit `trustedOrigins` built at boot; host-only cookies; Caddy overwrites `X-Forwarded-Host`; passkey `rpID` at the apex (one passkey for every host; passkeys are not built yet, P5); staff TOTP check in middleware. The apex itself serves only the national view, with no sign-in or form.

### ADR-14 Storage, Encryption and Backups

- **Context:** One disk holds Postgres, WAL, evidence and Docker's own data, which includes container environment values. A failing archiver fills `pg_wal` and Postgres PANICs. An unmounted LUKS volume makes Docker write plaintext to the root disk. The app tunnel runs in Docker, so it cannot carry the SSH session that unlocks the disk. Every backup sits in one Cloudflare account.
- **Decision:** One LUKS container, three LVs (`pgdata`, `files`, `docker`); the server's age key on the volume; passphrase unlock over a host-level, SSH-only tunnel; mount guards with binds into LV subdirectories; swap off or encrypted per boot; archiver and `backup_runs` checks in `/healthz/jobs`; pgBackRest and restic to separate R2 buckets with bucket locks if Free allows, plus a weekly mirror of the database repository to B2 whose age the server checks with a list-only key; rotation per key type; quarterly restore drill with reconciliation and a tenant-level restore.
- **Consequences:** Every reboot needs a person with Access SSH, but not physical access. TPM2 auto-unlock stays out, so a stolen server stays locked.

### ADR-15 Cross-Campus Forwarding

- **Status:** Superseded on 25 October 2026 by ADR-26: forwarding was removed and the rows it wrote stay for history.
- **Context:** A report can concern another campus's region or scope. The user chose no automatic routing: a report stays at the receiving campus, whose admins can forward it, which copies it and logs it in `audit_log` (Question 5). `withTenant` sets one tenant per transaction.
- **Decision:** `forwardReport` first locks the report under campus A and moves it to `forwarded` with compare-and-set and A's audit row; then, under B, it inserts the copy with `forwarded_from_report_id`, a new B code, status `in_review`, the reporter's membership in B if missing and an audit row, hard-links the evidence originals into B's directory, sends B's `evidence` jobs and emails the reporter B's tracking link with the original code (original first, so a concurrent reject at A cannot leave a copy at B for a rejected report). `UNIQUE (org_id, forwarded_from_report_id)` makes a retry finish the job without a second copy. `report_contacts` is not copied, because the reporter consented to campus A.
- **Consequences:** Two short transactions instead of one; a failure between them leaves A's original forwarded without a copy at B, which repeating the action resolves (the report page shows whether the copy exists). B's admins see no contact data; the reporter hears from B only through system status emails.

### ADR-16 Sign-Up, Sign-In and WhatsApp Delivery

- **Context:** The user decided on 16 October 2026 that every account holds a full name, an email address and a WhatsApp number, that a returning person signs in with either identifier, and that the person chooses where the code goes: email or WhatsApp. For WhatsApp the user chose an unofficial library after being told that the official Meta WhatsApp Business Platform charges per authentication message (the figure given was about Rp357 plus PPN in Indonesia; not re-checked against Meta's IDR rate card) and needs a verified Meta Business account, and that unofficial WhatsApp Web libraries break WhatsApp's terms, so the sending number can be banned at any time. Better Auth's `phoneNumber` plugin stores codes in plain text, signs in with a password, signs up with a temporary email, and lets admins skip TOTP.
- **Decision:** One Better Auth plugin of our own, `accountOtp`, for both channels (hashed codes, server-side identifier resolution, the two-factor after-hook reattached, the 18+ and phone checks in the user-creation hook). Email codes go out from `web`; WhatsApp codes go through the sealed `whatsapp-send` job to `worker-whatsapp`, which runs Baileys 6.7.24 (npm `baileys`, WhiskeySockets, the newest stable release; 7.0.0 is a release candidate) behind a provider interface. A Meta Cloud API adapter (copy-code authentication template) and a dev adapter (Mailpit) implement the same interface, chosen by `WHATSAPP_PROVIDER`. The superadmin links one dedicated number at `/admin/whatsapp` by QR or pairing code; the session credentials are sealed with a key only `worker-whatsapp` holds. Safety: per-number and sender rate limits, one short plain-text message with no link, a disabled WhatsApp option with a clear message when the sender is down, a visible failure with "Kirim lewat email" when a send fails, and `/healthz/jobs` reporting the sender state.
- **Consequences:** A ban or an outage of the number stops WhatsApp codes but never sign-in, because email always works. The switch path is a config change and a restart of `worker-whatsapp` (`WHATSAPP_PROVIDER=meta` with `META_WA_TOKEN`, `META_WA_PHONE_NUMBER_ID`, `META_WA_TEMPLATE`), after Meta approves the template, at a per-message cost. Triggers to switch: the number is banned, sends fail repeatedly, or the legal entity does not accept the risk. Known gaps (open questions): Daftar verifies only the chosen channel, accounts made before migration 0018 have no number, and identifier-first sign-in reveals whether an account exists. Never link a real number in dev and pick WhatsApp for a seed account. The sender handset is a credential (review round 2): whoever holds it, or a WhatsApp Web session linked to it, could read a live code and sign in as a non-admin user. Codes are sent disappearing (24 h) and the chat is deleted on the sender's devices right after the send; the handset stays locked with the superadmin, no other device is linked to the number, and `/admin/whatsapp` is checked at every on-call handover. A code sent to a number the account has not proven counts as a Daftar code, so Masuk cannot be used to message strangers past the Daftar caps. Second review round 2 (17 October 2026): codes to unproven email addresses have their own share (20 an hour, 60 a day, 10 a day per client address), as WhatsApp already had, so a Daftar flood cannot spend the provider day that proven sign-ins need; a graceful stop of `worker-whatsapp` writes `stopped`, which `/healthz/jobs` treats as deliberate, so the incident lever no longer hides every other alert; `whatsapp_auth` row keys carry an HMAC of the recipient id and contact sessions idle 30 days are pruned; sign-in code identifiers in `verifications` are HMACs and expired rows are deleted daily.

### ADR-21 Resumable Uploads

- **Context:** PLAN §7 step 5 and PLAN §13 Fase 2 ask for uploads that continue after a dropped connection. A 50 MB video over a weak mobile link that drops at 40 MB must today start again from byte 0 (`POST /api/upload/<evidence id>`, ADR-05). The upload resource already exists before any byte moves: the step-7 submit creates one `evidence` row per file, owned by the signed-in reporter, with its declared size. Every rule of ADR-05 must keep holding: owner only, the 24 h window, the type sniffed from the first bytes and matched to the row's kind, `EVIDENCE_LIMITS`, the per-tenant byte cap, the upload slots per process and per client, intake pause, load shedding, compare-and-set to `received`, then the `evidence` or `evidence-video` job (ClamAV for PDF, ffprobe for video). `web` mounts only `/files/evidence` read-write; `/scratch` belongs to `worker-media`.
- **Tooling evaluation (21 October 2026):** The protocol is tus 1.0.0 (tus.io, resumable-upload protocol), because clients exist for it (tus-js-client 4.3.1, MIT, released 16 January 2025) and its core is small: `HEAD` returns `Upload-Offset` and `Upload-Length`, `PATCH` with `Content-Type: application/offset+octet-stream` appends at `Upload-Offset`, 409 on an offset mismatch, `Tus-Resumable: 1.0.0` on every request and response except `OPTIONS` (412 otherwise), and `X-HTTP-Method-Override` honoured.
  - `@tus/server` (MIT): 2.4.6 was published on 17 October 2026, 4 days before this decision, so it fails the 14-day rule; the newest eligible release is 2.4.5 (31 August 2026). Releases are frequent (2.4.2 to 2.4.6 between July and October 2026). It brings five runtime dependencies, among them `srvx` ~0.11.15 (a 0.x request adapter), `debug`, `lodash.throttle`, `set-cookie-parser` and `@tus/utils`, 194 KB unpacked. Its model is "client `POST`s to create, the server mints the id"; serving an id it never created needs a custom `DataStore` (`create`, `getUpload`, `write` taking a Node `stream.Readable`), and `@tus/file-store` keeps a metadata file per upload next to the bytes. Its hooks (`onIncomingRequest`, `onUploadCreate`, `onUploadFinish`) run before the body or after the last byte, so the 415 at the first 4100 bytes would have to live inside our own store's `write` anyway. Its locker is in-memory per process (`MemoryLocker`), the same as ours.
  - Native: the tus core on the existing URL, no creation extension (the evidence row is the resource), offset taken from the size of a part file, in `server/api/upload.server.ts` next to the existing `POST`, sharing its row lookup, slots and commit. The module grew from 341 lines (Phase 1) to 823 after review round 2 on 21 October 2026 (the shared parts were split out of `POST` on the way), plus 19 tests, and needs no dependency.
  - **Chosen: native.** The library would give us header parsing and locking, both small, at the cost of a second bookkeeping model (its upload record next to our `evidence` row), a 0.x transitive adapter, and a custom store that holds all our rules anyway. Revisit if we need the creation, concatenation or expiration extensions, or uploads to object storage.
- **Decision:** `/api/upload/<evidence id>` serves tus 1.0.0 core in the same React Router resource route as the single `POST` (`app/routes/api/upload.ts` dispatches every method to `receiveUpload`, so the root middleware's tenant, CSRF Origin check and session apply, and `react-router dev` serves it too). Bytes go to `files/evidence/<org>/.part-<evidence id>`, opened for append; `Upload-Offset` is the file size, read fresh on each request. A `PATCH` holds one upload slot (the `web` load-shed pool and the per-process and per-client counters, shared with `POST`); a `HEAD` holds none. The type is sniffed once the part crosses the first 4100 bytes (415 and the part removed on a mismatch), and again at completion. A `PATCH` that would pass the declared size is 413 and the part is truncated back to its offset at the start of that request. A dropped connection, the per-request deadline (scaled to the remaining bytes, as for `POST`) or a takeover keep every byte already written. One in-process lock per evidence id: a new `PATCH` (or a `HEAD` that must commit) aborts a stalled holder and waits up to 3 s, else 423. When the part reaches the declared size it is hashed, the row moves to `received` by the same compare-and-set as `POST`, the part is renamed to the original and the job is sent in that transaction. A `HEAD` that finds a full part on a row still waiting (a commit that failed) commits it before answering. A successful `POST` removes any started part.
- **Consequences:** The single `POST` keeps its behaviour byte for byte, so the current frontend is unaffected. The lock and the slots assume one `web` process, as the compose file runs today; a second replica would need a Postgres advisory lock instead. The per-tenant daily byte cap counts started parts too (the sizes of the tenant's other `.part-*` files, added to the bytes received in the last 24 h, at every `POST` and `PATCH`; the file's own part is left out so it can finish), so stalled parts across many accounts cannot pass it; a part is bounded by its row's declared size, and parts not written for 24 h are removed by `maintenance-daily` with the `.tmp-` files. Parts are inside `/files/evidence`, so the nightly restic snapshot can include a part in flight, as it can a `.tmp-` file. A request the client abandons is logged as 500 by React Router (its handler rethrows the aborted signal after ours has kept the bytes); the client never sees it, and `POST` behaves the same. The client contract is in architecture.md (Resumable Upload Contract); the client is the frontend teammate's.

### ADR-22 Resolution Claims, Survey and Right of Reply

- **Context:** PLAN §5.7 opens a citizen rating round at every "Diklaim selesai" and closes it at "Selesai terkonfirmasi" or "Dibuka kembali" (user Question 9), allows one rating per account per claim with the account-age, IP-prefix and anomaly rules (user item 8, "Strict"), mails the reporters "Sudah beres?" four weeks after the claim, and lets "Selesai terkonfirmasi" come only from that survey or from an admin with linked proof. PLAN §5.5 moves the agency right of reply from the organisation's email to a form in Phase 2. The design here named `issues.current_claim_id` and the tables `resolution_claims`, `ratings` and `fix_surveys`.
- **Amended 25 October 2026 (ADR-26):** "Diklaim selesai" is gone (PLAN §5.4, line 246), so `applyIssueAction` no longer opens a round or enqueues `survey-send`; the survey and claim ratings reach only rounds opened before then, and when a survey should be sent now is an open team decision.
- **Decision:** Migration `0026_claims_ratings_replies` adds the three tables and `agency_replies`, all FORCE RLS. The current claim is the open `resolution_claims` row (partial unique index), not an `issues.current_claim_id` column: a column would make issues and claims reference each other, which breaks the foreign-key depth order `infra/tenant-export.sh` and `tenant-load.sh` rely on. `applyIssueAction` writes the round in the status-change transaction and enqueues `survey-send` with a 28-day `startAfter` (pg-boss keeps a deferred job until `start_after` plus retention). The survey rule is a pure function: one "belum beres" reopens at once, "sudah beres" from every invited reporter confirms, anything else waits for more answers or for an admin; the survey's transition runs through the same `applyIssueAction` with actor null and basis `survey`. Ratings are insert only. An accepted reply becomes a `responses` row through `record_response`, so it moves the government axis like any recorded response (it mailed followers until 25 October 2026); its source is the admin's link, the sender's link, or the issue page itself. New audit actions are stored as raw codes (`claim.survey_send`, `claim.survey_answer`, `reply.submit`, `reply.accept`, `reply.reject`), not added to `AUDIT_ACTIONS`, whose label map is frontend code; the same choice as `referral.remind`.
- **Consequences:** The pages are the frontend's ([contract](architecture.md#resolution-claims-survey-and-right-of-reply)). Open for the user: whether an admin confirm must carry an evidence link (PLAN §5.7 says so; the server accepts and stores `evidenceUrl` but does not require it, because the current confirm form has no such field and requiring it would block every admin confirm until the frontend adds one); whether one reporter's "belum beres" should reopen at once or wait for the admin; whether an accepted reply without a source link may cite the issue page; and whether admins get an email for a new reply (today only the `/kelola` queue). An issue claimed before migration 0026 got its open claim from the backfill but no survey job. The IP-prefix cap holds only while hashes exist (30 days); the prefix anomaly flag does not reset with them, because `maintenance-daily` stores each claim's top prefix count in `resolution_claims.max_prefix_ratings` before clearing (migration `0028_claim_prefix_max`, review round 3), rather than keeping hashes of open rounds past the 30 days `/privasi` promises. The reply quota is 5 per account per campus per 24 h, counted under `withTenant` like the complaint quota; a global count would need a second cross-tenant read path. Rounds with nobody reachable still write the `claim.survey_send` audit row (`reason_code` `no_recipient`). Rating does not purge the edge cache (up to 60 s stale). Review round 1 (21 October 2026): each survey notification names its round (`notifications.claim_id`, migration `0027_survey_claim`), so a mail deferred past a reopen and a new claim is skipped as `claim_closed` instead of linking the newer round the reporter was never invited to; and `SURVEY_ENABLED` (default `false`) holds every due survey, re-queued each morning, until the frontend ships `/isu/:code/survei`, because the mailed link would answer 404 before that.

### ADR-23 Agentic Testing Pattern for the Backend E2E Suite

- **Context:** On 21 October 2026 the user asked to use the pattern from Slack Engineering's "Agentic Testing: Where Agents Fit in the E2E Testing Stack" (Sergii Gorbachov, 11 June 2026, https://slack.engineering/agentic-testing-where-agents-fit-in-the-e2e-testing-stack/) and named tester-army/e2e. The article measures three approaches, among them one where "An AI agent generates deterministic Playwright test code from a natural language description", and concludes "Deterministic tests provide a stable foundation for CI," while "agentic testing adds a distinct layer at the top of the testing pyramid" "for exploration, debugging, and validating complex behaviors." The backend had unit and route tests but no end-to-end check of its HTTP contracts against a production build.
- **Tooling evaluation (21 October 2026), tester-army/e2e not adopted:**
  - `gh repo view tester-army/e2e --json createdAt,latestRelease,licenseInfo`: `"createdAt":"2026-07-22T09:29:04Z"`, latest release `"@e2e-dev/testmu@0.0.1"` with `"publishedAt":"2026-10-16T16:24:34Z"`, licence `apache-2.0`.
  - `bun info e2e version` and `bun info e2e repository.url`: `version = '0.21.2'`, `repository.url = 'git+https://github.com/tester-army/e2e.git'`. `bun info e2e time`: `"0.21.2": "2026-10-16T16:25:26.576Z"`, five days before this decision, so it fails the 14-day rule (the newest version older than 14 days is `"0.18.0": "2026-10-06T12:54:32.540Z"`). The npm name itself is older (`"0.0.1": "2014-12-16T18:32:55.964Z"`).
  - The README (fetched with `gh api repos/tester-army/e2e/readme`) says "e2e is in active development on the way to 1.0. APIs and config can still change between minor releases." Agent steps call a model when no recording matches: "An agent step that a later assertion verifies records its actions, and the next run replays them with no model calls until the app changes." So CI would need a model key and would run nondeterministically after any change. Telemetry is on unless disabled: "The CLI sends anonymous usage data ... Opt out with `npx e2e telemetry disable` or `E2E_TELEMETRY_DISABLED=1`."
  - It is a second runner beside Playwright 1.63.0, and its web engine (`@e2e-dev/web`, "Chromium, Firefox, and WebKit through Playwright") drives the browser UI, which the frontend teammate owns.
- **Decision:** Keep the article's generated-test approach without a model at run time. The agent writes each scenario as a plain-English test title, writes deterministic Playwright code for it, runs it against the production build on 127.0.0.1:5198, and refines it until it passes for the right reason. Only that plain code is committed, and CI runs it with no model. Backend only: `e2e/api.e2e.ts` uses Playwright's `request` fixture (`APIRequestContext`) and opens no page. The campus is picked by the `Host` header, and `X-Forwarded-Proto: https` stands in for Caddy, so HSTS, cookie and Origin rules run as in production. Each test sends its own random `X-Client-IP`, so rate-limit buckets and upload slots never carry over between tests or retries (the server keeps `X-Client-IP` when `TRUSTED_PROXY_IP` is unset, as in CI and local runs, and in production only from the proxy's address). The HSTS check reads `HSTS_POLICY` from the runner's environment and assumes the server has the same value (both unset in CI and locally, so `max-age=300`). Fixtures go through app code, not over the network: `e2e/api-fixtures.ts` (Bun) signs up a fresh reporter through Better Auth in process, creates a report with one `awaiting_upload` PNG through `handleSubmit` with the captcha stubbed (the step-7 action calls Cloudflare siteverify, a network dependency), and reads the codes the public must not see. `e2e/sign-in.ts` holds the sign-in steps shared with `e2e/staff-session.ts`; `signIn` deletes the account's own `email_log` rows before the send and again after verify-code, so every fixture account (a new timestamped reporter each run) leaves no `sign_up` row and repeated local runs on one database never fill the global Daftar quota (20 an hour, 60 a day; review round 2 hit a 503 in global setup after 19 runs in an hour). Reads compare against the sample seed's data (`db/seed/sample.ts`). The API scenarios have no sleeps: the only wait is `expect.poll` on the upload offset, and `e2e/sign-in.ts` waits for the captured code with `drainEmails()` and throws when none arrived. One deliberate sleep stays in the global setup, which runs for every project (`globalSetup` in `e2e/playwright.config.ts` is set once for the config, so `--project=api` runs it too, and `e2e/api.e2e.ts` reads the staff cookie it writes for the 'another account' upload refusal): `e2e/staff-session.ts` waits 1.1 s after `setSuperadmin`, because that call sets `users.updated_at = now()` from the database clock (`db/superadmin.ts`) and `verifiedSession` refuses a session created before it (`server/auth.server.ts`), while the new session's `createdAt` comes from the app clock. The `api` project in `e2e/playwright.config.ts` runs this file once (the `phone` and `desktop` projects ignore it) and in order (`fullyParallel: false`), so the fixture runs once per worker.
- **Consequences:** The scenarios cover the public data API (JSON and CSV, CC BY 4.0 in body and `Link`, ETag and 304, read-only CORS, k=5 suppression, unpublished, draft, cross-campus 404 and removed 410, no personal keys), the tus upload (fresh row, oversize 413, 401, other account, other campus, other site 403, 412, a connection cut mid-file through a raw socket and resumed from the stored offset, a repeat `POST`), the Better Auth 429 on the 21st lookup in 60 s from one client, the security headers and `Server-Timing`, and tenant isolation by host. The survey, rating and right-of-reply scenarios are `test.fixme`, because their routes (`/isu/:code/survei`, `/isu/:code/nilai`, `/isu/:code/hak-jawab`, `/kelola/hak-jawab`) are the frontend's and do not exist yet ([contract](architecture.md#resolution-claims-survey-and-right-of-reply)). Write them once those routes ship. The CI `e2e` job already runs every project through `bun run e2e` against its own seeded production server, so it runs the `api` project with no change to `ci.yml`. The fixture writes a reporter, a report and an upload into whatever database the run points at, so a local run must target a disposable copy, never the dev database. Revisit tester-army/e2e when it reaches 1.0, has a release older than 14 days, can replay with no model key in CI, and a UI suite is wanted with the frontend teammate's agreement.

### ADR-24 Coverage and Acceptance Gates

- **Context:** On 21 October 2026 the user asked for backend tests with "TDD, BDD, AND ATDD MINIMUM 97.5%". Workflow 11 made that measurable: TDD is aggregate line and function coverage of backend source of at least 97.5% from `bun test --coverage --coverage-reporter=lcov`; BDD is every backend acceptance criterion written as a Given / When / Then scenario in `docs/acceptance.md`; ATDD is at least 97.5% of those scenarios carrying an automated, non-skipped acceptance test that CI runs. Bun's lcov lists only the files some test loads: a backend file no test imports is not in the report at all, so the report's own totals overstate coverage (on 21 October 2026 `server/index.ts` was absent). Nothing in CI checked either number.
- **Decision:** Two gate scripts, each with its own tests, run in the `gates` job of `ci.yml`.
  - `infra/coverage-gate.ts` (`bun run coverage`, which runs the whole suite once with lcov into `coverage/` and then the gate). The CI Test step runs it inside the `media-test` image instead of `bun run test`, so the suite still runs once and nothing skips. Backend source is every `.ts` file from `git ls-files -co --exclude-standard` (tracked or untracked, not ignored, still on disk) under `server/`, `worker/`, `db/` (not `db/migrations/`), `shared/` and `infra/`, plus `app/**/*.server.ts` and the `.ts` resource routes under `app/routes/`, minus `*.test.ts`, `*.d.ts` and the test-only helper `db/testing.ts`. `worker/fixtures.ts` stays in: `db/seed/sample.ts` imports it. The gate fails when a backend file is missing from the lcov report, when aggregate lines or functions are below 99% (compared in integers, so 98.99% fails), when a file is below 90% lines, when it finds no backend source, and on a malformed lcov record (a missing `LF`, `LH`, `FNF` or `FNH`, or more hits than lines or functions) or a file listed twice. The per-file floor stops a large well-covered module from hiding an untested one. `FLOOR_EXCEPTIONS` in the script can excuse a file from the floor only, never from the report or the aggregate, needs a reason, must name a current backend file, and holds at most 5 entries; it starts empty.
  - `infra/acceptance-gate.ts` (`bun run acceptance`, a few seconds, no database). It reads the scenario headings of `docs/acceptance.md` (format in its Format section), checks each has a `Source:` line and Given, When, Then in order, then reads the test titles of every `*.test.ts` and `e2e/*.e2e.ts` file in the same git list. A scenario counts when a test carrying `[<ID>]` in its own title is neither skipped, todo, fixme, failing nor conditional, sits in no such `describe`, and has no `test.skip(...)` or `test.fixme(...)` statement in its body, an enclosing `describe` or the file. It fails below 99% automated, on zero scenarios, on duplicate or malformed IDs, on an ID under Out of Scope, and on any ID in a test title that the file does not define. `--trace` prints one line per tagged test (ID, file, title, counted or not). Review round 1 (22 October 2026) closed four holes: `xdescribe`, `xtest` and `xit` count as skipped; a test registered under `if`, `else`, `?:`, `&&` or `||`, or an `.each` over an empty table, does not count; the CI Test step passes `CI` into the `media-test` container so Bun refuses a stray `.only` (outside CI Bun runs only the focused test and the rest of the file passes silently), and Biome's `noFocusedTests` fails `bun run lint` on one. It also reads `check "[<ID>] ..."` lines of the shell tests in `SHELL_TESTS` (today `infra/stack-test.sh` and `infra/deploy-test.sh`, both run by the CI `image` job against a production compose stack; a gate test fails if `ci.yml` stops running one), and parses scenarios under "Pre-Launch Checks" (each needs a non-empty `Checked by:` line; review checks that it gives the exact command) without counting them in the share: they wait for the origin server, the Cloudflare zone or a B2 account, and the gate prints their number as `outside` so the exclusion is visible. Review round 2 (22 October 2026) replaced the condition list with a whitelist, because Bun registers nothing it does not reach on load (an early `return` in a `describe`, an uncalled helper, `for`, `while` and `catch` bodies all passed the round 1 check while `bun test` ran none of them): a tagged call counts only at the top of the file or directly in a `describe` callback body with no `return` before it in that body, and an `.each` only over a non-empty array literal. A loop-registered test therefore no longer counts, reversing round 1. The same round made the gate fail closed on a test file whose brackets do not balance (a regex the tokenizer misreads could otherwise end a skipped `describe` early), on any heading naming an ID that is not a level-three scenario heading, and on more than 2 scenarios outside the share (3 since the amendment below); the summary also prints `withOutside`, the share with those scenarios counted as open.
  - The tests are read from source, not from a runner report, because the Playwright suite runs in the `e2e` job against a production server and its results never reach the `gates` job. A small tokenizer skips comments and keeps strings, template literals and regex literals opaque, so a commented-out test or a test inside a fixture string is not read; checked by tagging every one of the 1,961 `test(` and `it(` calls of the 21 October 2026 tree, it found all 1,944 outside the fixture strings of its own test file, and counted all but the `e2e/flows.e2e.ts` test that calls `test.skip(...)` in its body. It stays conservative: a title built from a variable, a test called through an alias (`const heifTest = test.skipIf(...)`), a test registered anywhere but the top of the file or a `describe` callback body, and an ID in a `describe` title do not count. The gate cannot tell an HTTP-level test from a unit test; review checks that.
  - BDD without Cucumber: no Gherkin runner. The scenarios are Given / When / Then text in `docs/acceptance.md` and the steps live in the test title and body, run by `bun test` and Playwright as today. Cucumber would add a second test runner and a dependency, plus step-definition glue, for the same tests.
- **Consequences:** CI fails until coverage and the acceptance share reach the threshold, 99% since the amendment below (21 October 2026 baseline, 219 backend files: lines 93.49%, functions 93.8%, 12 files missing from the report, among them `server/index.ts` and 11 resource routes under `app/routes/`, 35 files below 90%, and no scenarios yet). `bun run coverage` needs `bun run db:up` like `bun run test`, and run outside the `media-test` image it skips the HEIC and qpdf tests, which lowers the numbers of the files they cover. Coverage is what Bun's JavaScriptCore counts as executable lines and functions; branches are not measured (Bun's lcov has no branch records). A tagged test that fails still counts as automated, because CI then fails on the test itself (the `gates` job for `*.test.ts`, the `e2e` job for `e2e/*.e2e.ts`). A new backend directory or a new test helper needs `isBackendSource` changed, with its test.
- **Amendment, 22 October 2026 (workflow 12):** The user raised both thresholds: "please continue with the best proper way (but only the backend) until all backend phase finish completely correct and consistent without any hallucination and error ; and please can use all the skills in the pstack, like verif, poteto, bug fix, and etc. MAKE SURE ALL INCLUDE THE TDD, BDD, AND ATDD MINIMUM 99% (please store this requirement pstac and testing e2e, edge, bug, etc to the claude md or agent md)". Both gates moved to 99% (`AGGREGATE_BP` 9750 to 9900 in `infra/coverage-gate.ts` and `infra/acceptance-gate.ts`, still compared in integers): their tests pin 9,900 of 10,000 passing and 9,899 (98.99%) failing, for lines, functions and scenarios, and 39 of 40 (97.5%) now failing. The per-file floor stays at 90% lines and the exception list at 5. Asked "How should these three count?" about the scenarios that wait for infrastructure, the user chose "Pre-launch checks (Recommended)": "Move the three to a 'Pre-Launch Checks' list in docs/acceptance.md, each with the exact command to run once the server, zone or B2 account exists. They leave the CI share, which becomes 136/136 = 100%. CLAUDE.md and the gate record that this list exists and stays at 3 or fewer." The section "Verified Outside This Gate" of `docs/acceptance.md` became "Pre-Launch Checks" and holds AC-LOAD-01 (production origin), AC-EDGE-01 (Cloudflare zone) and AC-RESTORE-01 (B2 account), each with a `Checked by:` line giving the exact command. AC-RESTORE-01 moved from Scenarios, where it was the one open scenario: its local drill `infra/restore-test.sh` already runs in CI's `image` job and only the B2 copy step waits. No other scenario moved or changed. `MAX_PRE_LAUNCH` is 3, a fourth fails the gate, and a gate test pins the three IDs of the real file, so a fourth needs a reviewed change to that test. The JSON keys `outside` and `withOutside` stay. `bun run acceptance` on 22 October 2026 after the move: `{"msg":"acceptance-gate","scenarios":136,"automated":136,"percent":100,"open":0,"outside":3,"withOutside":97.84,"problems":0}`. Functions coverage read 98.51% and 98.55% in workflow 11's gate runs, so `bun run coverage` fails at 99% until functions are raised.

- **Consequences:** Retention of declined originals is an open team decision. `maintenance-daily` deletes the evidence of a `rejected` report 90 days after its last update (PLAN §11, line 1099: "berkas asli laporan yang tidak diterbitkan: 90 hari setelah ditolak"), but no request reaches `rejected` any more, so the originals of every newly declined report, now `unverifiable`, are kept with no end date. `unverifiable` is not final: `REPORT_TRANSITIONS.verify` still starts from it, so a report can be verified later. Two options for the team. (A) After 90 days in `unverifiable` the report can no longer be verified and its originals are deleted; this changes what the admin's "Verifikasi" form does on old reports, a frontend behaviour the backend does not change on its own. (B) Bring back a reject action and form, so a decline reaches `rejected` and the existing purge. Until the team picks one, the backend keeps the current behaviour (no purge of `unverifiable` originals) rather than deleting evidence an admin can still act on; the retention row in architecture.md says so.
